# Security model and qualification

## Authorization source of truth

The publishable source path opens a fresh reader/table scan, with `SourceProjectionClient.iter_rows` retained as a guarded wrapper. For each configured reader/table it verifies the Dataverse organization and the enabled human's Dataverse-to-Entra identity binding. A complete table-specific privilege lookup that explicitly includes Basic team privileges can prove absence of table Read: that produces no rows and no table permission without attempting impersonation. This supports new unroled users and complete role removal. For every data-producing projection, `CallerObjectId` executes queries as the reader and the configured identity proof first verifies the actual execution context. This is either the default `eq-userid` FetchXML query or the explicitly configured, code-pinned [Custom API proof](READ-CONTEXT-PLUGIN.md). An impersonated WhoAmI response alone is never proof; the adapter never automatically falls back between identity modes.

Metadata maps table Read through `EntityDefinitions.Privileges`, avoiding name-derived mappings such as confusing Activity with a physical table. Each reader/table gate uses `RetrieveUserPrivilegeByPrivilegeId(PrivilegeId=<table Read GUID>,ExcludeTeamBasic=false)` and consumes the complete response. Every returned grant must match the requested privilege GUID. The result establishes privilege presence, not record access or a locally inferred effective depth. An empty valid result produces no source rows and omits the table permission; an HTTP 403, failed identity binding, foreign privilege GUID or incomplete response fails the scan. The source data query evaluates contributing row and field rules. [Specific privilege API](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/reference/retrieveuserprivilegebyprivilegeid?view=dataverse-latest)

The September 21 hydration exposed a concrete undergrant in the earlier general `RetrieveUserPrivileges` gate: it omitted Account Read for team-only Basic personas who could retrieve team-owned Accounts. A general-inventory absence is therefore not accepted as proof of no table Read. See `reports/hydration-review-20260921/team-basic-gate-diagnostic.json`. The gate and row iterator share one fresh per-pair scan; they do not cache grants across readers or tables, expose a caller-supplied bypass flag, or omit identity and operator qualification.

This approach includes Basic ownership, Local and Deep business units, Global Read, team ownership/membership, access-team and POA sharing, inherited sharing, source hierarchy behavior and applicable column profiles/record-specific field shares through their effect on the source response. It does not require copying the whole authorization graph into Fabric. It also does not claim that the local shadow evaluator is a complete replacement for Dataverse.

The operator needs appropriate impersonation, source and field permissions. The adapter requires Global Read and verifies selected secured-field coverage using the immutable built-in System Administrator role-template GUID or all-record Read grants from complete direct/team field-profile discovery. Missing coverage blocks projection; per-record POAA is not sufficient to qualify the operator's all-record scope. The System Administrator template is identified by GUID, not role display name. [Microsoft's role-template explanation](https://www.microsoft.com/en-us/dynamics-365/blog/no-audience/2009/07/09/rolling-with-the-system-administrator-role/)

Custom source plug-ins, conditional source behavior and engine-specific field behavior can still influence query results. Actual operator/reader parity must be qualified. The contract is the selected scalar Dataverse read projection under the verified reader context, not every API message or application presentation mode.

## Field security and data representation

The adapter selects explicit scalar properties, preserves returned values, fills omitted selected fields with NULL, and discards properties outside the configured projection. Configured masking is discovered from `attributemaskingrules`; no unmask operation or `UnMaskedData` parameter is used. NULL and masked values are persisted separately for each reader. A field grant alone cannot create a row because rows must first be returned by Dataverse.

Native OneLake CLS permits only the configured business columns and hides the helper fields. Native CLS is not used to turn a denied field into NULL; that result already exists in the materialized row. Users see the source's selected-query result, including NULL when returned. Decimal JSON values are parsed as Decimal; the writer preserves supported typed values. Unsupported attributes or security metadata fail closed instead of silently dropping a field.

Microsoft describes [column security and masking](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/column-level-security) and [record-specific field-security examples](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/samples/column-level-security-powershell). These source features still need deliberate negative and revocation fixtures in the destination qualification.

## Serving boundary

Each physical serving row has two trusted helper values: `__pw_reader` is an Entra object ID, and `__pw_generation` is the immutable generation number. A reader's role contains a literal filter on both values and the business-column allowlist in the same rule. The application rejects wildcard/helper column exposure, unsafe identifiers, duplicate identities and over-budget plans. Role names are owned by a deployment prefix.

Only the publisher may write these helper values or the serving tables. Consumers must not have write, workspace elevation, raw-storage read, broad item data access, foreign OneLake roles, delegated SQL access or shortcuts that bypass the intended controls. OneLake roles are cumulative; an additional broad grant defeats a narrower role. The publisher rejects potentially overlapping foreign grants rather than trying to subtract them.

SQL endpoints require verified user identity mode for this native design, or must be inaccessible to the audience. A delegated SQL endpoint uses a different authorization boundary and cannot be assumed to enforce the reader's OneLake role. Spark, SQL, Direct Lake and downstream semantic models must each be explicitly approved and tested. Disabling an unqualified access path is an operational boundary, not a change to source Read permissions.

The provided boundary file is a trusted controller/operator assertion. Its schema and 15-minute age check do not cryptographically prove the external facts. The publisher additionally inspects supported workspace assignments and role conflicts, but group expansion, alternate item/storage grants and SQL mode still require a truthful external inspection. A timestamp editor is not a boundary provider.

This is an unfinished integration for unattended publication, not a completed scanner hidden behind configuration. A production provider must inspect the exact shard audience, expand relevant group membership, inventory alternate grants and data routes, verify the SQL mode, and refuse a fresh assertion if any fact is unavailable. Microsoft documents the SQL mode check through the endpoint's [data access mode settings](https://learn.microsoft.com/en-us/fabric/onelake/security/sql-analytics-endpoint-onelake-security). The [admin item-access inventory API](https://learn.microsoft.com/en-us/rest/api/fabric/admin/items/list-item-access-details) is explicitly preview and not recommended for production use in its reference. Qualify the bank's inspection mechanisms and administrator change controls; do not infer a closed boundary from a successful role API response.

## Temporal consistency

Source reads use `Consistency: Strong` to request current cached metadata and permissions, with no claim of a multi-request transaction. Pages are origin- and collection-bound; repeated continuations, malformed payloads, duplicate record IDs, failed requests and exceeded row/page/time budgets invalidate the scan. [Dataverse request headers](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/compose-http-requests-handle-errors)

Preparation start is the conservative generation freshness anchor. A long scan cannot extend its lease by setting a new completion timestamp. Publication requires a complete immutable manifest, matching configuration, staged hashes, current deadline, current boundary and successful destination policy validation. A new generation is appended privately before its role predicates become active. Retired readers/shards are withdrawn.

The generation condition rejects a retained prior-generation row when the current policy is evaluated. This is not proof that every historical-query feature, previously opened transaction, cached role or cached result applies the current predicate. Tests must establish the behavior for each allowed engine. Data already exported or copied by an authorized user cannot be retroactively revoked by this adapter.

An independent watchdog removes owned roles when a generation expires. This is an active control-plane operation, not a self-expiring native predicate. Fabric outage, stale engine policies, long-running queries, cached results or a dead watchdog can prevent timely revocation. The code exposes that limitation; it does not assert a proven 60-minute hard bound. Production requires measured propagation reserves, independent incident containment and approved behavior during control-plane failure.

If the 60-minute deadline must also hold while Fabric's policy-update API is unavailable, direct native access with these static roles does not satisfy that requirement. A separately qualified serving boundary must evaluate expiry at query time and prevent direct access around it. Successful watchdog experiments or a larger role quota cannot remove this architectural limitation.

The separately deployable `native_watchdog` reads role generations directly, so it can withdraw access after publisher-host or journal loss. It validates ownership and canonical policy shape, uses ETags and cannot renew grants. Its configuration still must enumerate every serving item, and its own identity, scheduler and availability remain part of the qualified boundary. See the [independent watchdog deployment](../deploy/README.md).

## Publication and recovery invariants

- Projection source operations are GET-only. Administrative source discovery is never substituted for the reader's data response. The separate explicit plug-in installer creates only its reviewed Dataverse customization components.
- All previously yielded rows are provisional until the source scan and generation finish successfully.
- Local manifests bind source observations, configuration, reader/table membership, data hashes and the planned role generation.
- ETags protect role collection updates. PUT replaces the full role collection, so unowned roles are preserved and conflicts block publication.
- Policy mutations are not blindly retried. Ambiguous commits trigger inspection/quarantine and withdrawal attempts, not restoration of older access.
- A successful role GET/digest comparison proves the control plane's state only. It does not prove current consumer enforcement.
- Configuration changes, schema changes or source failures require a fresh generation. Hash edits and manual authorization rollback are not recovery procedures.
- The loopback console is an operator aid, not an authenticated public service. Raw staging data and identity mappings are privileged local artifacts.

## Release qualification

Use a protected fixture set with distinguishable values, explicit expected readers and deliberate denied cases. Do not use only System Administrator users. Confirm the end user's direct source session agrees with the impersonated source projection before comparing Fabric. Every enabled target access path needs the same comparison.

1. **Read depths and ownership:** user-owned Basic positive; another user's same-BU Basic negative; team-owned Basic; Local own-BU positive and sibling negative; Deep descendants positive and outside-subtree negative; Global positive. Exercise roles anchored in multiple BUs and modern owning-BU behavior.
2. **Cumulative grants:** overlapping direct roles, team roles, default teams and access teams; remove one grant while another independently retains access. Verify one physical result row per reader/record and unchanged aggregates despite overlapping reasons.
3. **POA:** direct user share, owner/access-team share, inherited/cascaded share, POA-only record access and missing-table-Read negative. Revoke each share and prove the row disappears within the approved bound. Exercise relevant principal types rather than assuming every POA row names a user.
4. **Column profiles:** readable row with a denied secured field returns the expected NULL; direct and team profile grants; multiple profile union; profile and membership revocation; secured lookup behavior actually supported by the tenant; masked value where configured.
5. **Record-specific fields:** populate and revoke real `principalobjectattributeaccess` fixtures. Grant a field for one readable row, deny it for another, and verify a field-only grant cannot expose an otherwise unreadable row. Test profile plus record-share grant overlap.
6. **Identity lifecycle:** disabled/deleted reader, removed role, removed team membership, changed BU, changed record owner, removed table Read and out-of-audience identity. Verify their Fabric sessions cannot use an old grant after the approved interval.
7. **Query shapes:** exact selected values, filters on denied/masked fields, NULL predicates, counts, sums, grouping, joins, sort, explicit projections and `SELECT *` behavior. Count/value digests should agree with the intended source representation; native CLS errors must be documented for consumers.
8. **Bypass paths:** elevated workspace membership including groups, broad item grants, default OneLake roles, delegated SQL, storage/shortcut access and exposed helper fields must deny or block publication. Recheck group inheritance under real tenant membership.
9. **Failure and history:** dropped source pages, throttling, late completion, publisher crash between shards, ETag conflict, post-commit timeout, expired boundary, old Delta versions, old transactions, old sessions, caches, stopped watchdog and Fabric control-plane outage. Observe actual remaining access and containment behavior.
10. **Scale:** increase through the actual 200-reader population toward 1,000 using realistic rows/reader, field diversity, POA sharing and table count. Measure source throttling, request count, generation duration, Delta storage, role propagation and query performance. A 1,000-reader planner test is not a 1,000-reader service benchmark.

Store timestamps, source/target version or generation IDs, tested principals, expected/actual allowed record sets, field outcomes and engine identities as controlled evidence. A single unauthorized result is a release failure. Under-granting and source NULL mismatches are also parity failures. Record what remains untested rather than marking all features qualified from a positive smoke test.

## Native access and the 60-minute boundary

The selected requirement retains native Fabric access, including the required Spark, OneLake and Direct Lake paths, and a maximum 60-minute security-change delay. The deadline has not been waived during Fabric role-control API outages. A SQL-only or API-only service that checks expiry on each query does not satisfy these selected access paths. The query-time boundary discussed above is therefore not an accepted replacement for this deployment.

Official Microsoft documentation reviewed on **2026-09-19 at 03:49 UTC** establishes the following limits:

- **No documented native lease:** the published `DataAccessRole` and `MicrosoftEntraMember` schemas expose no expiry, lease or activation-window field. Updating or removing a role remains a control-plane operation. This is a statement about the published contract, not a claim that Microsoft could never offer another capability. [Role and membership REST schema](https://learn.microsoft.com/en-us/rest/api/fabric/core/onelake-data-access-security/create-or-update-data-access-roles)
- **No documented clock predicate:** OneLake RLS compares a column against static values; the supported syntax does not include `GETUTCDATE()` or `CURRENT_TIMESTAMP`. A literal generation filter cannot expire itself. The REST `RowConstraint` description nevertheless mentions dynamic and multitable RLS. That wording conflicts with the product limitations and the SQL troubleshooting guidance, which directs dynamic policies to delegated SQL mode. Do not infer native support from the REST prose without Microsoft's explicit supported contract. [RLS syntax](https://learn.microsoft.com/en-us/fabric/onelake/security/row-level-security-syntax), [native RLS limitations](https://learn.microsoft.com/en-us/fabric/onelake/security/row-level-security), [SQL clarification](https://learn.microsoft.com/en-us/fabric/onelake/security/troubleshoot-onelake-security-for-sql-analytics-endpoints#rls-and-cls-constraints)
- **PIM expiry does not bound Fabric enforcement:** PIM can remove an expired group membership within seconds, but Microsoft warns that cached application access can persist. OneLake's integration documentation describes approximately one hour for Entra group-membership changes and possible additional engine caching. This is not a hard maximum within the 60-minute budget. [PIM deactivation](https://learn.microsoft.com/en-us/entra/id-governance/privileged-identity-management/groups-activate-roles), [OneLake propagation and caching](https://learn.microsoft.com/en-us/fabric/onelake/security/onelake-security-integrations-external-engines#latency-considerations)
- **SAS expiry is not native-role expiry:** OneLake SAS and delegation keys last at most one hour and are scoped to files or folders. Direct Lake requires Entra authentication and explicitly does not support SAS authentication. Expiring a SAS does not remove a user's existing native Entra-based grant. [OneLake SAS](https://learn.microsoft.com/en-us/fabric/onelake/onelake-shared-access-signature-overview), [Direct Lake authentication](https://learn.microsoft.com/en-us/fabric/fundamentals/direct-lake-security-integration#authentication-requirements)
- **Engine checks still need qualification:** Spark caches effective-access metadata for the duration of a query; the documented behavior does not promise to terminate an existing query on revocation. SQL user-identity mode documents up to five minutes for synchronization after a role changes. Direct Lake documents refresh requirements for security-configuration changes, including shortcut changes. None of these statements provides an all-engine revocation deadline when the role change itself cannot complete. [Spark caching](https://learn.microsoft.com/en-us/fabric/data-engineering/spark-onelake-security#performance-considerations), [SQL synchronization](https://learn.microsoft.com/en-us/fabric/onelake/security/sql-analytics-endpoint-onelake-security), [Direct Lake limitations](https://learn.microsoft.com/en-us/fabric/fundamentals/direct-lake-security-integration#considerations-and-limitations)

Consequently, the independent watchdog's 45-minute generation lifetime and five-minute schedule are an operational budget, not a server-enforced expiration guarantee. More watchdogs or additional successful normal-operation tests do not resolve the missing outage enforcement mechanism. **Production release remains blocked on a Microsoft-supported native expiry mechanism or a qualified independent containment mechanism that covers every required native path within 60 minutes.** The adapter must not label this requirement satisfied from control-plane withdrawal evidence alone.

Workspace customer-managed key (CMK) revocation is a promising independent emergency stop: Microsoft documents that workspace read/write calls fail within 60 minutes after key revocation. Detection and trigger delay precede that allowance, so this alone does not prove 60 minutes from a Dataverse change. It also requires an eligible capacity and workspace: trial capacity and mirrored Dataverse workspaces are excluded, and semantic-model encryption has separate considerations. It was not enabled or tested in this demo. Key Vault key expiration is not a substitute for explicit revocation: expired keys can still decrypt and unwrap. [Fabric workspace CMK](https://learn.microsoft.com/en-us/fabric/security/workspace-customer-managed-keys), [Key Vault key attributes](https://learn.microsoft.com/en-us/azure/key-vault/keys/about-keys-details)

Deleting or tombstoning expired projections is not an all-engine expiry proof either. Delta retains historical physical data until vacuum, while Direct Lake can retain columns from a framed Delta version in memory. Physical deletion can stop subsequent cold reads without establishing denial for warm models or in-flight queries. Storage leases govern writes/deletion and do not require a lease ID for ordinary reads. These mechanisms may support containment, but require separate native-engine experiments and cannot be represented as closing the deadline. [Delta history](https://learn.microsoft.com/en-us/fabric/data-engineering/delta-lake-time-travel), [VACUUM](https://learn.microsoft.com/en-us/fabric/data-engineering/delta-lake-vacuum), [Direct Lake storage behavior](https://learn.microsoft.com/en-us/fabric/fundamentals/direct-lake-understand-storage), [Blob lease operations](https://learn.microsoft.com/en-us/rest/api/storageservices/lease-blob)

Escalate these concrete questions to Microsoft and retain the response as release evidence:

1. Is a server-enforced OneLake role or membership lease available that expires without a successful `dataAccessRoles` update? Provide the supported API, tenant availability and enforcement semantics.
2. Is a query-time UTC expiry predicate supported across Spark, SQL user-identity mode and Direct Lake on OneLake? Provide exact syntax and resolve the conflicting `RowConstraint` documentation.
3. What maximum delays apply to new queries, already running queries, policy caches and result caches after revocation, including a role-control API outage?
4. Which independently controlled containment operation blocks every required native read path when policy updates fail, with a documented deadline and failure behavior?

Any proposed answer still requires tenant qualification against actual consumer identities and outage fixtures. Neither an undocumented API nor a successful dry run establishes a supported expiry contract.
