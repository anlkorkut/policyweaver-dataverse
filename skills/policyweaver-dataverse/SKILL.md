# Policy Weaver Dataverse

Configure and operate the cloned application for the client's own tenant and artifacts. Locate the repository using the current workspace and confirm `pyproject.toml`, `policyweaver/adapter_cli.py` and `docs/CLIENT-ONBOARDING.md` exist. All application paths below are relative to that repository, never to an assumed laptop path or a previous demonstration deployment. An installed copy of this skill is guidance, not a bundled application.

For a **new client**, read `docs/CLIENT-ONBOARDING.md` and `docs/CLIENT-INPUTS.md`. Use the repository's onboarding commands to discover evidence and render a validated configuration; do not replace GUIDs in a demonstration configuration. For an **existing deployment, publication, incident or schedule**, read [references/operations.md](references/operations.md), then the relevant application runbook sections. Inspect the checked-out CLI's `--help` when behavior is uncertain.

## New-client intake

1. Explain the three components: the optional Dataverse `pw_ReadContext` Custom API proves execution identity; the Python adapter reads and materializes the selected source data as each reader; native OneLake roles restrict those reader-specific projections. It preserves effective source Read results rather than copying each named Dataverse role one for one.
2. Collect the tenant ID, Dataverse HTTPS origin and intended operator identity first. Reuse facts and authorization already supplied in the session. Inspect authentication without exposing tokens; an active CLI account or a familiar display name does not establish the correct tenant, immutable identity or source organization. Onboarding checks the expected operator UPN/object ID during discovery only. Runtime Azure CLI credentials are tenant-bound and do not retain that operator pin: use an isolated `AZURE_CONFIG_DIR` and recheck the intended active account before operations, especially after reader acceptance sign-ins. The plan's operator field is audit evidence, not a runtime restriction.
3. Run read-only discovery. Record what was actually observed, its time and any incomplete scope. Discover organization ID, eligible Dataverse/Entra bindings, table metadata and accessible Fabric workspaces/items. The Power Platform environment ID is separate from the organization ID; do not substitute it. Do not guess missing IDs, treat a permissions error as an empty inventory, or default to all readers/tables.
4. Ask only for unresolved choices that change the deployment: exact reader cohort, logical tables/scalar columns, destination workspace and isolated serving-item scope, required consumer engines, security-change deadline and hosting mode. Have the client choose from discovered evidence. Resolve UPNs to immutable IDs and detect ambiguity; names are for review, IDs bind authorization. No reader password is needed for extraction.
5. Render a new private client directory with typed configuration, input/selection evidence and a reviewable plan. Use readable names, timed retention and one source worker for a new client unless the client explicitly chooses otherwise. Confirm quotas for the selected items; a support exception in another environment does not transfer. Leave the publication boundary unverified until a real inspection. A valid template is not permission to publish.
6. Continue the operating sequence below within the authorized scope. Complete the concrete plan and local checks before seeking any missing deployment authorization. Routine reads and local preparation do not require repeated confirmation. State the exact external change and its scope if approval is still needed; creating source components, adding workspace privileges, replacing customer policies or disrupting unrelated SQL queries is not implied by asking for an inventory.

## Operating sequence

1. Validate the exact client configuration and plan. Existing items require verified ownership and an explicit scope decision; never adopt a raw linked lakehouse or match an item by name alone. Keep client inputs, inventory, local business data and logs out of the repository's tracked content.
2. Use the repository bootstrap or install in a 64-bit Python 3.11+ virtual environment with `python -m pip install -c requirements.lock -e ".[adapter,test]"`; run appropriate tests. Use Azure CLI for local work or a configured managed identity on an identity-enabled host for unattended operation. Never place tokens, passwords or signing keys in configuration or logs. `.env` files do not configure the adapter automatically.
3. Use `doctor` and `discover` to establish actual source readiness. Entra licenses do not prove Dataverse user hydration. Every data-producing projection must verify impersonated execution context; do not substitute administrator data reads or an unverified WhoAmI result. An administratively verified enabled-human binding plus complete proof of absent table Read instead produces zero rows and no table permission, without an impersonated data query. A failed request or identity binding is never an absent-Read proof.
   For readers without `prvReadUser`, use the [identity-proof guidance](references/operations.md#identity-proof-without-extra-reader-privileges), the application's `docs/READ-CONTEXT-PLUGIN.md` and the installed registration CLI. The optional Custom API proof requires a reviewed signed DLL hash, exact verified metadata and real header-switch tests. Choose the first-registration or managed-import path appropriate to the environment. Installing it creates Dataverse customization components and must remain within the user's authorized source deployment scope. Reuse existing authorization; do not broaden reader roles, fabricate proof, switch modes automatically or publish an unqualified proof path.
4. Prepare a complete generation and inspect its status, reader/table coverage, source metrics, age and shard plan. Preparation writes sensitive local data. Keep the state directory private. Preserve failed-generation evidence without publishing its partial rows.
5. Within the user's authorized deployment scope, provision separate private serving lakehouses. Provisioning changes configuration, so prepare a new generation afterwards. Verify the minimal reader entry permissions, perform the policy dry run and inspect the actual serving boundary. Native SQL requires UserIdentity mode and a supported lakehouse owner; service-principal ownership is currently unsupported for SQL security sync. Check the actual owner, not merely the creator. New native roles alone do not provide item entry Read. Publication requires a boundary covering the exact audience, verified SQL mode and real inspection time. Never fabricate its booleans, update only its timestamp or interpret a dry run as runtime qualification.
6. Before the first timed publication, have the independent watchdog operational and monitored with the exact serving items, namespace, compatible version and retention mode. Verify its actual identity rights and healthy withdrawal-mode execution; a template or inspect-only job provides no expiry protection. Publish only a complete, current generation through the application, then validate actual consumer queries on each enabled engine. Ongoing publication also needs a trusted source of fresh boundary inspections; a static attestation cannot sustain automated publication.

## Preserve these distinctions

- Authoritative mode uses Dataverse `CallerObjectId` read results. Basic, BU, teams, POA and field NULL/masking behavior are evaluated at source. The shadow authorization evaluator cannot publish.
- The current adapter performs full projections of selected reader/table pairs. It has no complete security delta collector, automatic boundary inspector or distributed publisher journal. A timer does not add those capabilities. Benchmark the client's selected scope and end-to-end change-to-enforcement time before promising a cadence or user count.
- Actual-reader SQL qualification can use explicit `bound_whoami` with a controlled Dataverse/Entra ID pair and matching delegated credentials. This direct-user proof removes the reader's `prvReadUser` dependency; it must not replace the adapter's impersonated execution proof.
- For native role names, read `docs/READABLE-ROLES-AND-DIVERSITY.md`. New onboarding uses `role_naming: "user_business_role"`: username, home BU and one prioritized source role title, with action words removed. No added PW prefix or ID suffix. Require version 0.3.1 or later on every publisher and independent watchdog before fresh preparation/publication: ownership is now bound by a canonical RLS annotation plus member/tenant/path checks. The annotation is not a secret or authorization grant. Preserve full source-role provenance and reject naming collisions. Existing `legacy`/`readable` modes remain compatible. Never manually rename policies or infer access from a displayed role/home BU. The SQL-compatible limit is 124 alphanumeric characters.
- All selected scalar field results, including NULL, must be preserved. Native CLS hides helper columns; it does not reconstruct Dataverse's record-specific field behavior. Unsupported attributes/security metadata are a scope blocker, not permission to silently omit them.
- A verified lack of table Read is different from HTTP 403, malformed metadata or a failed page. Errors invalidate publication; they are not empty successful results.
- The planner accepts at most 1,000 readers. Role quotas, table quotas, source throughput, materialization size and the measured revocation bound remain separate constraints. Support quota exceptions are specific to confirmed destination items.
- SQL delegated identity, workspace elevation, broad item grants, foreign roles, storage access and shortcuts can bypass the native role boundary. Do not grant broad access to fix an authorization test.
- A role update and generation condition do not establish cache invalidation or immediate expiry. The watchdog actively withdraws roles; a Fabric control-plane outage can prevent it. Report the actual enforcement evidence and remaining gates.
- If the user explicitly chooses persistent roles, use the application's `retention_mode: "manual"` before a fresh preparation and align every publisher and independent watchdog for the exact deployment scope. Read `docs/MANUAL-RETENTION.md`. This waives age-based withdrawal, not acquisition/publication freshness or explicit withdrawal. Do not simulate persistence with an infinite timestamp, edited manifest, or globally disabled watchdog.
- If native Fabric paths and a hard 60-minute deadline during policy-API outages are both required, treat native expiry as a platform dependency. More watchdogs, role slots or successful dry runs cannot supply an engine-enforced lease. Preserve both requirements and seek a supported native mechanism; do not silently substitute SQL/API-only access or waive the deadline.

## Completion and recovery

Report the client configuration path, verified tenant/organization/workspace, exact selected scope, artifacts created, executed commands, tests, active generation and any unqualified engines or fixtures. Distinguish discovered, selected, prepared, published and reader-verified states. Do not call the deployment enterprise-qualified merely because offline tests and role APIs succeeded. The required negative, field-profile, POAA and revocation tests are in `docs/ADAPTER-SECURITY.md`; use `docs/LIVE-ACCEPTANCE.md` for actual-reader SQL checks.

For failures, use `status` and the safe journal error codes. Do not restore older grants after an ambiguous publication, bypass ETags, edit manifests or clear a live writer lock. Use `withdraw` or the watchdog when access must be contained; confirm consumer denial separately. Continue authorized preparation and diagnostics while external setup is pending, and identify the exact missing fact when a dependent step cannot proceed.
